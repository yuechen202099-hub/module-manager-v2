# ChatGPT 产品经理接手说明书

文档日期：2026-06-22  
当前产品版本：V2.6.5  
适用对象：ChatGPT 产品经理、项目主管、需求分析线程、新加入的协作智能体  
定位：让新的产品经理快速理解产品、业务、现状、边界和下一步指挥方式。

## 1. 一句话介绍

模块更换项目管理器 V2 是一个面向电表/模块改造项目的生产协作系统，用于把“总清单、扫码照片、施工采集、资料审阅、异常闭环、终端交付、人员 KPI”串成一套低成本、多人协同、可上线使用的工程管理软件。

系统当前不是演示原型，而是已经上线运行的生产工具。后续工作要以“稳定生产、提升效率、减少返工、方便考核”为第一原则。

## 2. 产品解决的问题

现场模块改造项目存在几个核心痛点：

1. 数据来源复杂  
   总清单、扫码表格、施工员拍照、小程序/网页采集、外部图片 URL、OSS 图片、本地上传照片同时存在。

2. 表号匹配容易出错  
   长条码、短表号、扫码内容和总清单字段不完全一致，需要统一匹配规则。

3. 多人协作容易冲突  
   管理员、审阅员、施工员各自负责不同流程，同一终端不能被多人同时误操作。

4. 审阅效率是关键  
   审阅员需要快速看图、快捷键分类、归档、补图、转异常或回退未施工。

5. 施工现场网络不稳定  
   施工员必须支持手机端采集、本地缓存、恢复网络后统一上传。

6. 异常和未匹配需要闭环  
   错表号、错采集器、错模块、缺照片、未施工、项目外施工、换表，都需要留痕和回流。

7. 管理者需要真实进度和 KPI  
   管理员需要按终端、安装人员、日期、有效工时、完成量、异常数、地址难度等维度看项目状态。

## 3. 当前用户角色

### 管理员

主要职责：

- 导入总清单。
- 导入扫码表格。
- 创建和维护账号。
- 指派施工任务。
- 收回或调整审阅/施工任务。
- 查看项目看板和系统状态。
- 导出异常表计、终端交付包和 KPI 数据。
- 判断项目风险并安排现场返工。

关键页面：

- `/project-board`
- `/claim-tasks`
- `/task-hall`
- `/construction`

### 审阅员

主要职责：

- 按终端领取审阅任务。
- 查看资料组照片。
- 使用快捷键进行照片分类。
- 归档资料组。
- 删除错误照片。
- 补图。
- 转异常工单。
- 回退未施工。

关键页面：

- `/claim-tasks`
- `/task-hall`

### 施工员

主要职责：

- 处理管理员指派的终端施工任务。
- 手机端扫码录入表号、采集器号、模块号。
- 拍照或从相册选择照片。
- 离线缓存资料组。
- 联网后上传缓存。
- 处理异常工单或现场补图。
- 完成后提交施工任务，释放当前终端。

关键页面：

- `/construction`
- 微信小程序施工端

## 4. 核心业务流程

### 4.1 管理员导入总清单

总清单是安装地址唯一来源。  
安装地址不能去重，必须和表号/资料组一一对应。  
后续阶段清单不再作为核心流程。

总清单导入后的核心数据：

- 表号
- 匹配键
- 终端
- 安装地址
- 安装人员或原始人员字段

### 4.2 管理员导入扫码表格

扫码表格包含：

- 扫码内容/表号
- 采集器
- 模块资产编号
- 图片 URL
- 创建者/安装人员
- 扫码时间

导入原则：

- 不按表号整组跳过。
- 按照片级去重。
- 已存在照片不重复下载、不重复上传 OSS。
- 同表号新增照片可以补入资料组。
- 未匹配表号进入未匹配/异常处理流程。

### 4.3 任务领取

审阅任务按终端组织。

审阅员：

- 只应看到自己可领取或已领取的有效任务。
- 重点是有未审阅内容的终端。

管理员：

- 可以看到全部终端。
- 可以收回任务。
- 可以查看上传率、审阅率、已归档、未审阅等状态。

### 4.4 审阅工作台

审阅工作台是产品效率核心。

核心动作：

- 选择终端。
- 选择资料组。
- 查看完整图片。
- 缩略图切换。
- 快捷键分类。
- 保存资料组。
- 归档当前图或当前资料组。
- 删除照片。
- 补图。
- 转异常工单。
- 回退未施工。

必须保持：

- 键盘操作流畅。
- 图片完整显示，不裁切关键区域。
- 已归档照片仍可被重新选中和修改。
- 重复标签不能直接归档，应提示修改。
- 未施工资料组默认折叠或弱化，避免干扰主要审阅。

### 4.5 施工采集

施工采集以手机端体验为主。

核心动作：

- 选择被指派终端。
- 搜索地址或表号。
- 点击资料组打开采集单。
- 扫码录入表号、采集器、模块号。
- 拍照或从相册选择。
- 保存到本地缓存。
- 一键上传缓存。
- 提交施工任务，释放当前终端。

照片槽位：

- 改造前照片，必填。
- 采集器照片，可选。
- 模块与电表照片，必填。
- 改造后照片，必填。

注意：

- 模块号必填。
- 现场网络弱时，必须先入本地缓存，再上传，避免数据丢失。
- 一个施工员最多同时处理 5 个 active 终端任务。
- 施工端和微信小程序原则上功能要同步。

### 4.6 异常处理

异常处理已经并入审阅工作台，不再作为独立页面主流程。

异常来源：

- 表号错误。
- 采集器号错误。
- 模块号错误。
- 照片错误。
- 照片缺失。
- 现场无法施工。
- 项目外施工。
- 换表。

异常处理原则：

- 地址来自总清单，默认不在审阅中修改。
- 表号、采集器、模块号可以被修正。
- 转异常工单应保留原资料组已有采集器号和模块号。
- 只有回退未施工/回退施工时才清空采集器、模块和照片。
- 异常数据需要支持导出给现场处理。

## 7. 数据与图片策略

### 数据事实源

当前目标事实源是 PostgreSQL。  
历史 JSON 状态仍保留兼容和回滚价值，但不能作为长期架构方向。

### 图片来源

系统可能同时遇到：

- 外部 URL 图片。
- 本地上传图片。
- OSS 图片。
- 服务器静默缓存图片。

产品策略：

- 审阅列表和卡片优先加载缩略图/预览图。
- 大图查看使用预览级图片即可，除非用户明确需要原图。
- 导出也可以优先使用预览图标准，以降低成本和等待时间。
- 已归档组可以由服务器静默缓存图片，后续导出优先从服务器取。
- 避免重复下载和重复上传。

## 8. KPI 和管理视角

当前产品已经有安装人员 KPI。

核心指标：

- 每日工作量。
- 开工时间。
- 收工时间。
- 有效工时。
- 长时间停顿不计入有效工时。
- 2 小时时段分布。
- 每小时有效工时完成量。
- 地址集中度/零散度权重。
- 异常数量。

地址权重原则：

- 同一 `号` 或同一 `弄+号` 默认视为同一工作簇。
- 公用设备在同一栋楼内应和住户地址一起计算。
- 缺少室号通常意味着商铺、别墅或现场寻找难度更高。
- 充电桩/车位地址寻找难度较高，但同区域充电桩可部分复用寻找路径。

产品经理要注意：

- KPI 只能辅助管理，不能作为绝对惩罚依据。
- 需要持续让现场反馈修正权重。
- 每个 KPI 数字最好可点开看到原始地址清单和依据。

## 9. 当前生产与发布规则

当前生产域名：

- `https://www.sgcc.online`

生产规则：

- 优先补丁发布，不要每次整包替换。
- 发布前必须备份。
- 不覆盖生产 `.env`。
- 不覆盖生产 `data`。
- 不覆盖 uploads。
- 不擅自执行 Alembic。
- 小改动版本号 `+0.0.1`。
- 大改动版本号 `+0.1.0`。
- 发布后验证 `/health`、`/login`、`/project-board`、`/task-hall`、`/construction`。
- 生产 `/openapi.json` 应返回 404。

## 10. 协作规则

项目已经采用多线程/多智能体协作模式。

协作原则：

- BUG 修复线程负责定位和修复 Bug。
- 项目工程师线程负责新增功能、发布、架构调整。
- 产品经理负责需求优先级、验收标准、流程取舍和用户体验判断。
- 任何改动都要先看：
  - `PROJECT_KNOWLEDGE.md`
  - `BUG_HISTORY.md`
  - `FIX_NOTES.md`
  - `docs/AGENT_COORDINATION.md`
- 每次实际修改都要写：
  - `docs/V2_CHANGE_WORKLOG.md`
- 不允许两个线程抢同一个版本号。
- 不允许未经确认覆盖别人正在改的文件。
- 文档、版本、commit、tag、发布记录要闭环。

## 11. 产品经理接手后的工作方式

### 第一步：先确认当前目标

每次开始前先问：

- 这是 Bug、体验优化、功能新增，还是架构工程化？
- 是否影响生产？
- 是否需要立刻发布？
- 是否需要小程序同步？
- 是否涉及数据库迁移？
- 是否会改变审阅员或施工员的核心路径？

### 第二步：按优先级排队

推荐优先级：

1. 生产不可用、数据丢失、无法登录、无法上传、无法审阅。
2. 会导致现场返工或数据错配的问题。
3. 会明显降低施工员/审阅员效率的问题。
4. 管理员看板和 KPI 可信度问题。
5. UI 美观和操作舒适度问题。
6. 架构优化和长期工程化。

### 第三步：每个需求必须写验收标准

好的验收标准格式：

```text
角色：
入口：
前置数据：
操作步骤：
预期结果：
异常情况：
是否需要移动端验证：
是否需要小程序同步：
是否需要发布：
```

### 第四步：禁止含糊发布

发布前必须明确：

- 版本号。
- commit。
- tag。
- 备份路径。
- 是否 Alembic。
- 是否覆盖数据。
- 验证页面。
- 回滚方式。

## 12. 当前产品优势

1. 已经跑通真实生产链路。  
   这不是纯原型，已经覆盖登录、导入、审阅、施工、缓存、导出、KPI、发布备份。

2. 成本控制好。  
   当前预算较低，采用单服务器、PostgreSQL、自建服务和 OSS/本地混合策略。

3. 业务贴近现场。  
   很多规则来自真实施工和审阅反馈，例如快捷键审阅、离线缓存、按终端任务、回退未施工、施工提交。

4. 迭代速度快。  
   已经形成补丁发布和版本记录机制。

5. 可追溯性逐步增强。  
   版本、备份、BUG_HISTORY、FIX_NOTES、WORKLOG、协调文档已经形成闭环。

## 13. 当前产品不足

1. 历史架构负担较重。  
   `local_simulation.py` 和 `state_repository.py` 仍然承担大量历史逻辑，维护成本高。

2. JSON 兼容历史仍未完全退出。  
   PostgreSQL 是目标，但仍存在历史兼容路径。

3. 图片链路复杂。  
   外部 URL、本地、OSS、代理、缩略图、缓存、导出并存，容易出现灰图、半图、成本和速度问题。

4. Vue 和小程序同步压力大。  
   施工采集端要求网页和小程序一致，后续 PM 必须明确双端同步验收。

5. UI 还需要持续打磨。  
   产品已经可用，但要达到“愿意付费”的高级感，还需要统一视觉语言、交互细节和移动端体验。

6. 自动化测试覆盖仍不够完整。  
   后端测试较多，前端真实浏览器交互和手机端自动化仍不足。

## 14. 推荐下一阶段路线

### P0：生产稳定

- 固化每日自动备份和恢复演练。
- 增加系统健康页的告警可读性。
- 确保所有上传、导入、导出都有失败可恢复路径。
- 确保施工员提交任务后任务生命周期完整闭环。

### P1：审阅效率提升

- 审阅页图片加载继续优化。
- 大图查看、缩放、拖动体验打磨。
- 键盘流转和自动滚动持续优化。
- 已归档照片可修改逻辑继续稳定。

### P1：施工端移动体验

- 手机端施工采集布局继续简化。
- 采集单打开速度、缓存可见性、上传反馈优化。
- 小程序和网页施工端功能对齐。

### P2：KPI 产品化

- KPI 规则参数化。
- 每个指标可解释。
- 地址权重支持人工校正。
- 导出面向管理考核的报表。

### P2：图片成本和性能

- 统一缩略图/预览图策略。
- 已归档资料服务器静默缓存。
- OSS 读取和流量成本持续优化。
- 避免重复下载和重复上传。

### P3：工程化

- PostgreSQL 完全替代 JSON 事实源。
- 仓储层瘦身。
- 前端 E2E 和手机端测试自动化。
- 日志、审计、监控和告警完善。

## 16. PM 决策红线

以下事情不要轻易批准：

- 没有备份就上线。
- 为小 Bug 做整包覆盖发布。
- 未确认生产数据结构就执行 Alembic。
- 同时改多个核心流程。
- 因为 UI 细节大改业务逻辑。
- 把隐藏/取消的旧静态功能重新激活。
- 让施工端和网页端规则不一致。
- 把账号密码、Token、OSS 密钥写入文档或提交。
- 全量下载全部图片做导出。
- 在生产库上测试新功能。

## 17. PM 每周检查清单

- 生产是否可登录。
- 今日导入是否成功。
- 今日施工上传是否成功。
- 审阅员是否有未完成任务卡住。
- 施工员是否有长期占用终端未提交。
- 异常表计是否可导出。
- 单终端交付包是否可导出。
- 图片是否有明显灰图/半图。
- 备份是否在 24 小时内成功。
- 磁盘和 OSS 成本是否异常。
- KPI 是否出现不合理安装人员或日期。
- BUG_HISTORY 和 FIX_NOTES 是否同步更新。

## 18. 最重要的一句话

这个产品的价值不是“页面多”，而是让现场施工、资料审阅和项目管理形成一个可追溯、可回滚、低成本、能真正减少返工的闭环。
